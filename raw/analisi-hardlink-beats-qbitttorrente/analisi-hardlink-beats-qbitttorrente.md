Analisi dell'Integrità dei Collegamenti Fisici NFS e del Seeding con qBittorrent nel Tagging con BeetsVincoli di Filesystem e Coesistenza degli Hard Link su Condivisioni NFSPer valutare gli effetti delle modifiche apportate dall'applicazione Beets all'interno della directory Pluto sui file originali presenti nella directory Pippo (gestita da qBittorrent), è fondamentale analizzare la natura dei collegamenti fisici (hard link) in un contesto di rete basato su Network File System (NFS). Un collegamento fisico non è un puntatore o una scorciatoia, bensì una voce di directory aggiuntiva che associa un nome di file direttamente a un numero di inode esistente sullo stesso filesystem. Di conseguenza, più voci di directory possono fare riferimento allo stesso inode, condividendone i medesimi blocchi di dati sul disco.Tuttavia, gli hard link presentano un limite strutturale invalicabile: non possono estendersi oltre i confini di un singolo filesystem o dispositivo logico. Poiché la directory Pippo è montata tramite il protocollo NFS, la directory Pluto deve risiedere obbligatoriamente all'interno dello stesso identico punto di montaggio NFS e sullo stesso volume logico del server di storage. Se Pluto fosse posizionata su un filesystem locale (ad esempio, sul disco rigido locale del client che monta Pippo), qualsiasi tentativo di creare un hard link fallirebbe immediatamente restituendo un errore di collegamento incrociato tra dispositivi (EXDEV o OSError: [Errno 18] Cross-device link). Assumendo che questo prerequisito fondamentale sia soddisfatto e che l'hard link iniziale sia stato stabilito correttamente all'interno dello stesso export NFS, l'interazione con Beets e qBittorrent segue precise dinamiche di sistema.Dinamica dei Dati nella Directory PippoNel momento in cui si utilizza l'applicazione Beets per alterare i metadati dei file musicali nella directory Pluto, il destino dei dati all'interno della directory Pippo dipende strettamente dal meccanismo di scrittura impiegato dalla libreria Python sottostante, Mutagen. Di default, Beets è configurato con l'opzione write: yes, il che significa che l'applicazione tenterà di scrivere i tag aggiornati direttamente all'interno dei file musicali.Se Mutagen esegue una modifica dei metadati in loco (in-place), i byte del file originale vengono modificati direttamente sovrascrivendo i blocchi di dati associati all'inode condiviso. Poiché Pippo e Pluto puntano allo stesso inode sul server NFS, qualsiasi alterazione fisica dei dati si riflette istantaneamente e simultaneamente su entrambi i percorsi. Di conseguenza, i file musicali in Pippo subiranno una modifica interna dei propri byte, compromettendo la loro integrità originale.Tuttavia, se la modifica dei metadati richiede una ristrutturazione profonda del file (come nel caso dell'inserimento di copertine ad alta risoluzione o quando lo spazio di riempimento dell'intestazione del file è insufficiente), Mutagen e Beets adottano una strategia di salvataggio atomica. Questo processo prevede la scrittura dei nuovi dati all'interno di un file temporaneo in una directory di staging. Una volta completata la scrittura, il file temporaneo viene rinominato per sostituire il file di destinazione in Pluto. Questa operazione di ridenominazione rompe il collegamento fisico originario. Di conseguenza, il file in Pluto farà riferimento a un nuovo inode con i metadati aggiornati, mentre il file in Pippo continuerà a puntare al vecchio inode, preservando i dati originali senza alcuna modifica.Conservazione o Rottura del Collegamento FisicoLa conservazione dell'hard link tra Pippo e Pluto è determinata dalla combinazione delle operazioni di tagging e di ridenominazione dei file eseguite da Beets. Quando Beets viene configurato per riorganizzare la libreria rinominando i file in base ai nuovi metadati (ad esempio, modificando la struttura dei nomi in Pluto tramite il comando beet move), il sistema operativo esegue una chiamata di ridenominazione all'interno dello stesso filesystem.La ridenominazione di un file non modifica il suo inode, ma altera semplicemente la voce di directory associata ad esso. Poiché gli hard link sono record di directory completamente indipendenti l'uno dall'altro, la modifica del nome di un file all'interno di Pluto non ha alcuna ripercussione sul nome del file corrispondente in Pippo. Il file in Pippo manterrà il suo nome originario (quello atteso da qBittorrent), mentre in Pluto lo stesso inode sarà accessibile sotto un nome e un percorso completamente diversi. Sebbene la connessione fisica sia preservata dal punto di vista del filesystem, la ridenominazione in combinazione con la riscrittura dei tag può portare a comportamenti divergenti:Scrittura in-place riuscita: L'hard link viene mantenuto, l'inode è lo stesso, ma i nomi dei file differiscono tra Pippo e Pluto. I dati interni sono modificati in entrambi i percorsi.Scrittura tramite file temporaneo (salvataggio atomico): L'hard link viene interrotto. Pluto conterrà un nuovo file con nome e metadati aggiornati su un nuovo inode. Pippo manterrà il file originale, con il vecchio nome e i vecchi metadati, sul vecchio inode.Comportamento di qBittorrent e Verifica dell'HashLa capacità di qBittorrent di continuare a condividere (eseguire il seeding) i file musicali nella directory Pippo senza riscontrare anomalie dipende interamente dallo stato dei byte associati all'inode registrato nel client torrent. I client BitTorrent monitorano l'integrità dei dati suddividendo i file del torrent in pezzi logici di dimensioni fisse e verificandone l'impronta crittografica tramite hash SHA-1.Se l'hard link viene interrotto durante l'aggiornamento dei metadati (scenario del salvataggio atomico via file temporaneo), qBittorrent non subirà alcun impatto. Il file in Pippo rimarrà associato all'inode originario, i cui byte non sono stati alterati, consentendo al client di continuare il seeding in modo del tutto trasparente. Il principale svantaggio di questo scenario è la perdita del risparmio di spazio derivante dall'hard link, in quanto i file diventeranno duplicati fisici indipendenti sul server NFS.Se l'hard link viene preservato e Beets modifica i metadati in-place, i byte del file in Pippo vengono alterati. Al primo controllo di coerenza dei dati (eseguito da qBittorrent all'avvio, durante un controllo forzato o in caso di errore di lettura dei blocchi), il client identificherà una mancata corrispondenza dell'hash per i pezzi del file che contengono i tag modificati. Questo innescherà le seguenti conseguenze:qBittorrent rileverà i pezzi modificati come corrotti.Il client arresterà la condivisione di quei blocchi e avvierà automaticamente il download dei pezzi corretti dalla rete peer-to-peer per ripristinare lo stato originale del file.Il download andrà a sovrascrivere i dati sul disco. Poiché l'hard link è ancora attivo, la sovrascrittura ripristinerà i byte originari anche all'interno della directory Pluto, annullando di fatto tutte le modifiche ai metadati apportate da Beets.Per quanto riguarda la ridenominazione dei file, poiché la modifica del nome in Pluto non influenza la voce di directory in Pippo, qBittorrent non riscontrerà errori di tipo "file mancante", a patto che il percorso e il nome del file all'interno di Pippo rimangano rigorosamente inalterati.Matrice di Compatibilità delle Configurazioni BeetsLa tabella seguente illustra l'impatto sui file e sull'operatività di qBittorrent in base alle diverse opzioni di configurazione definite nel file config.yaml di Beets:Configurazione Beets (config.yaml)Comportamento di Scrittura in PlutoIntegrità dell'Hard LinkEffetto sui Dati in PippoStato del Seeding in qBittorrentwrite: yes[cite: 8, 9]move: no[cite: 8, 9](Modifica in-place)Scrittura dei tag direttamente sul file esistente.Preservato.I metadati in Pippo vengono alterati.Fallito: Errore di hash check; Beets viene istruito a gestire i tag modificati e i nomi dei file esclusivamente all'interno del proprio database SQLite. Per implementare questa modalità, è necessario modificare il file di configurazione config.yaml impostando i seguenti parametri:YAMLimport:
    write: no
    copy: no
    move: no
    hardlink: yes
In questo modo, l'hard link viene preservato indefinitamente e qBittorrent può continuare il seeding senza alcun rischio di errore di hash, poiché i byte fisici sul filesystem NFS non subiscono alcuna modifica. La ridenominazione dei file e l'aggiornamento dei metadati saranno visibili all'interno delle applicazioni che si interfacciano direttamente con il database di Beets.Soluzione B: Uso dei Reflink (Copy-on-Write)Qualora il server di storage NFS utilizzi un filesystem che supporta la tecnologia Copy-on-Write (CoW), come Btrfs o OpenZFS, è possibile configurare Beets per utilizzare i reflink al posto degli hard link tradizionali. I reflink consentono a più file di condividere gli stessi blocchi di dati sul disco fino a quando uno dei file non viene modificato; in quel momento, il filesystem duplica automaticamente e in modo trasparente solo i blocchi alterati. La configurazione consigliata in questo caso è:YAMLimport:
    reflink: yes
    write: yes
Questa impostazione garantisce che qualsiasi modifica apportata da Beets ai metadati dei file in Pluto causi la duplicazione automatica del solo blocco contenente l'header del file, lasciando il file originale in Pippo completamente intatto. Ciò salvaguarda l'operatività di qBittorrent e ottimizza al contempo lo spazio complessivo occupato sul disco.
