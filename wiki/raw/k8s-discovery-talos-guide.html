Kubernetes Discovery — Cluster Talos on-premise

Guida operativa completa per la configurazione del Discovery ServiceNow su cluster K8s on-site • Release Australia Patch 3 • Basata su documentazione ufficiale ServiceNow

Diagnosi: perche il Discovery Kubernetes non compare nello scheduling serverless

Causa radice identificata

Il Discovery Kubernetes di tipo on-premise non viene presentato come voce autonoma nelle opzioni di scheduling serverless della UI standard. Le voci visibili (GCP, AWS, Azure) sono generate automaticamente dai pattern cloud infrastructure (Get Kubernetes Clusters) solo quando si dispone di un Cloud Service Account configurato per uno di quei provider.

Per un cluster Talos on-premise — che non appartiene a nessun cloud provider — occorre creare lo schedule serverless manualmente, seguendo il percorso distinto documentato per il discovery on-premise con pattern Kubernetes e, nel vostro caso specifico, sfruttare la modalita Credential-less / MID-in-cluster poiche il MID Server e gia deployato all'interno del cluster.

Nota importante — Discovery and Service Mapping Patterns: Il pattern Kubernetes non e incluso nel plugin base com.snc.discovery. Richiede l'applicazione separata Discovery and Service Mapping Patterns (sn_itom_pattern) installabile dal ServiceNow Store. Verificarne la presenza prima di procedere. [Fonte: servicenow-australia-it-operations-management-enus.pdf, pp. 950-951]

Prerequisiti da verificare prima di iniziare

Su ServiceNow
  • Plugin com.snc.discovery attivo (gia confermato)
  • App Discovery and Service Mapping Patterns (sn_itom_pattern) installata da Store
  • MID Server registrato e Up nella console MID (gia confermato)
  • Ruolo admin o discovery_admin sull'istanza
Sul cluster Talos / K8s
  • MID Server deployato nel namespace sn (gia confermato)
  • ServiceAccount sn-discovery-sa + ClusterRole sn-discovery-read-role applicati (gia presenti nel vostro RBAC)
  • API server raggiungibile dall'interno del cluster
  • Kubernetes versione 1.34 (versione validata per release Australia)
Versione Kubernetes validata: On-Premises Kubernetes 1.34. [Fonte: servicenow-australia-it-operations-management-enus.pdf, p. 950]

Procedura passo per passo

Fase A — Verifica e installazione dell'applicazione Patterns

  1. Verificare l'installazione di Discovery and Service Mapping Patterns
    Navigare in:
    All > System Applications > All Available Applications > All
    Cercare l'applicazione Discovery and Service Mapping Patterns (sn_itom_pattern). Se compare il pulsante Install anziche Installed, installare la versione piu recente disponibile. Questa e la causa principale del problema: senza questa app, il pattern Kubernetes non esiste nell'istanza.
  2. Verificare la presenza del pattern Kubernetes nel Pattern Designer
    Navigare in:
    All > Pattern Designer > Discovery Patterns
    Cercare la stringa Kubernetes. Devono essere visibili almeno:
    • Kubernetes (pattern principale)
    • Kubernetes Event (pattern eventi)
    Se non sono presenti, l'applicazione sn_itom_pattern non e installata o non e aggiornata.

Fase B — Estrazione del Bearer Token dal cluster Talos (modalita standard con credenziali)

Alternativa semplificata disponibile: poiche il MID Server e gia deployato all'interno del cluster, e possibile usare la modalita Credential-less (Fase C) che elimina la necessita di gestire il token. Si consiglia di valutare prima la Fase C. La Fase B serve come fallback o se si preferisce autenticazione esplicita.
  1. Ottenere l'URL dell'API server Talos
    Eseguire sul cluster: 
    kubectl cluster-info
    L'output mostra la riga: Kubernetes control plane is running at https://<IP>:<PORT> Annotare l'URL completo compreso di protocollo e porta (es. https://10.x.x.x:6443).
  2. Ottenere i namespace
    Eseguire: 
    kubectl get namespaces
    Annotare i namespace rilevanti. Il namespace kube-system e obbligatorio nel campo namespace dello schedule.
  3. Estrarre il Bearer Token dal ServiceAccount sn-discovery-sa
    Poiche Talos usa Kubernetes moderno (versione 1.24+), i token non vengono piu creati automaticamente come Secret. Creare un token temporaneo dal ServiceAccount gia esistente: 
    kubectl create token sn-discovery-sa -n sn --duration=8760h
    Questo restituisce un token JWT. Copiarlo interamente: sara necessario nel campo Bearer Token di ServiceNow.

    In alternativa, verificare se esiste un Secret associato: 
    kubectl describe secret -n sn
  4. Creare le credenziali Kubernetes su ServiceNow
    Navigare in:
    All > Discovery > Credentials
    Selezionare New, poi scegliere Kubernetes Credentials. Compilare i seguenti campi:
Campo Valore da inserire per il cluster Talos Note
Name K8s-Talos-OnPrem-Cred (nome descrittivo univoco) Libero, deve essere riconoscibile
Bearer Token Authentication Selezionare la checkbox Bearer Token Authentication Abilita il campo Bearer Token; non usare username/password insieme al token
Bearer Token Incollare il token JWT estratto in formato BASE64 Usare solo uno dei due metodi: username/password oppure Bearer Token
Credential alias Creare un nuovo alias: selezionare l'icona lucchetto > icona lente > New > nome k8s-talos-alias, Type = Credential L'alias e obbligatorio per il collegamento allo schedule serverless
Regola esclusiva: usare esclusivamente il Bearer Token oppure Username/Password. Non entrambi contemporaneamente. [Fonte: servicenow-australia-it-operations-management-enus.pdf, pp. 953-954]

Fase C — Modalita Credential-less / MID-in-cluster (percorso consigliato per il vostro setup)

Prerequisito: il MID Server deve essere deployato come container all'interno del cluster Kubernetes. Nel vostro caso e gia soddisfatto (namespace sn, Deployment confermato). In questa modalita non e necessario configurare credenziali Kubernetes: il MID Server si autentica automaticamente all'API server tramite il ServiceAccount del pod. [Fonte: servicenow-australia-it-operations-management-enus.pdf, pp. 961-962]
  1. Verificare che il ServiceAccount del pod MID abbia i permessi corretti
    Il ClusterRole sn-discovery-read-role nel vostro YAML e gia corretto e copre tutti gli endpoint richiesti dal pattern Kubernetes: /api/v1/nodes, /api/v1/pods, /api/v1/services, /apis/apps/v1/deployments, /apis/apps/v1/statefulsets, /apis/apps/v1/daemonsets, /apis/apps/v1/replicasets, /apis/networking.k8s.io/v1/ingresses, /apis/batch/v1/jobs, /apis/batch/v1/cronjobs.
    Verificare con: 
    kubectl auth can-i list pods --as=system:serviceaccount:sn:sn-discovery-sa -n default

Fase D — Creazione dello schedule serverless Kubernetes (passaggi GUI dettagliati)

  1. Aprire la creazione dello schedule di Discovery
    Navigare in:
    All > Discovery > Discovery Schedules
    Selezionare New.
  2. Impostare il tipo di Discovery come Serverless
    Nel form dello schedule, impostare il campo Discover su Serverless.
    Attenzione: questo e il campo che determina le opzioni successive. Non scegliere IP Range o altri tipi: per Kubernetes on-premise va usato il tipo Serverless.
  3. Selezionare il Pattern Kubernetes
    Dopo aver scelto Serverless, comparira il campo Pattern (o Execution Pattern).
    Cliccare sull'icona di ricerca e cercare Kubernetes.
    Selezionare il pattern denominato Kubernetes (non i pattern GCP/AWS/Azure che sono cloud-specific e causano esattamente il sintomo descritto).

    Causa del problema originale  I pattern cloud (GCP – Get Kubernetes Clusters, AWS – Get Kubernetes Clusters, Azure – Get Kubernetes Clusters) compaiono solo dopo la configurazione di un Cloud Service Account. Il pattern Kubernetes puro deve essere selezionato manualmente da questo campo.
  4. Compilare il campo Name dello schedule
    Inserire un nome descrittivo univoco, ad esempio: K8s-Talos-OnPrem-Discovery
  5. Assegnare il MID Server
    Nel campo MID Server, selezionare il MID Server deployato nel cluster Talos (nel vostro caso: MID_Server_K8s / hostname k8s-lab-mid-server).
    E fondamentale selezionare il MID Server che risiede fisicamente nel cluster, in modo che la Credential-less discovery funzioni tramite il ServiceAccount del pod.
  6. Configurare gli Execution Pattern Attributes
    Nella sezione Execution Pattern Attributes (o Attributes) compilare i campi seguenti. Seguire la tabella riportata di seguito in base alla modalita scelta.
Modalita Credential-less (MID-in-cluster) — consigliata per il vostro setup
Campo (Execution Pattern Attribute) Valore da inserire Descrizione
url https://kubernetes.default.svc
oppure
https://cluster		 URL interno all'API server Kubernetes raggiungibile dal pod MID. In Talos, l'endpoint standard e https://kubernetes.default.svc
namespace *, kube-system (tutti i namespace)
oppure
sn, default, kube-system (selettivo)		 Elenco namespace separati da virgola. kube-system e sempre obbligatorio. Usare * per tutti.
cluster_name talos-onprem-cluster (nome univoco a scelta) Nome che identifica il cluster nel CMDB. Deve essere univoco. Non richiede formato speciale nella modalita on-premise.
credentials alias Lasciare vuoto Non richiesto in modalita credential-less: il MID Server usa il proprio ServiceAccount

cluster_resource_id Lasciare vuoto Applicabile solo per cluster cloud (Azure Resource ID, AWS ARN, GCP global name)
Modalita con Bearer Token (alternativa — Fase B)
Campo (Execution Pattern Attribute) Valore da inserire Descrizione
url https://<IP-control-plane>:6443 URL dell'API server Talos (es. VIP del control-plane se HA, o IP di uno dei tre nodi). Includere protocollo e porta.

  1. Impostare la frequenza di esecuzione
    Impostare il campo Run secondo le esigenze operative. Valori supportati: Daily, On Demand, Weekdays, Weekends, Month Last Day, Calendar Quarter End.
    Raccomandazione: iniziare con On Demand per il test iniziale, poi passare a Daily.
  2. Salvare e attivare lo schedule
    Selezionare Submit o Update per salvare il record. Lo schedule appare nella lista Discovery Schedules con stato Active. Per lanciare il primo discovery manualmente: aprire il record e selezionare Execute Now.

Fase E — Creazione dello schedule per Kubernetes Events (opzionale ma raccomandato)

Il pattern Kubernetes Event aggiorna il CMDB con gli eventi del cluster in modo incrementale. Al primo avvio registra un event_timestamp; nelle esecuzioni successive raccoglie solo i delta. Configurarlo con frequenza di 5-10 minuti. [Fonte: servicenow-australia-it-operations-management-enus.pdf, p. 955]

  1. Creare un secondo schedule serverless
    Seguire la stessa procedura della Fase D, selezionando il pattern Kubernetes Event (anziche Kubernetes). Configurare gli stessi attributi di esecuzione (URL, namespace, cluster_name).
  2. Impostare frequenza a 5 o 10 minuti
    Nel campo Run scegliere la frequenza piu breve disponibile. Piu frequente e l'esecuzione, minore e il numero di update CMDB-IRE necessari a mantenere lo stato aggiornato.

Fase F — Proprieta di sistema rilevanti (sys_properties.list)

Queste proprieta controllano il comportamento del discovery Kubernetes a livello globale. Navigare in: All > sys_properties.list e verificare / impostare i valori seguenti. [Fonte: servicenow-australia-it-operations-management-enus.pdf, pp. 958-961]

Property Name Valore raccomandato Descrizione
sn_itom_pattern.k8s_midserver MID_Server_K8s Nome del MID Server da usare per il discovery Kubernetes
sn_itom_pattern.k8s_create_schedule-enabled false (per on-premise) Impostare true solo per cloud (GCP/AWS/Azure): crea automaticamente schedules per i cluster cloud. Per on-premise lasciare false per non generare schedule indesiderati.
sn_itom_k8s_run_ck Da validare Se abilitata, esegue i pattern cloud Kubernetes senza creare auto-schedules. Verificare se necessario per l'ambiente specifico.

Verifica post-esecuzione

  1. Verificare lo stato di Discovery
    Navigare in:
    All > Discovery > Discovery Status
    Cercare la riga corrispondente allo schedule K8s-Talos-OnPrem-Discovery. Lo stato deve evolvere da Running a Completed senza errori critici.
  2. Verificare i CI creati nel CMDB
    Navigare in:
    All > Configuration > Kubernetes Cluster
    Tabella: cmdb_ci_kubernetes_cluster. Devono comparire record con il cluster_name impostato.
    Verificare anche: cmdb_ci_kubernetes_node, cmdb_ci_kubernetes_pod, cmdb_ci_kubernetes_service, cmdb_ci_kubernetes_deployment.
  3. Controllare i log del MID Server in caso di errori
    Navigare in:
    All > MID Server > Log
    Filtrare per il MID Server MID_Server_K8s. Cercare errori di connessione all'API server o problemi di autorizzazione RBAC.

Riepilogo decisionale — quale percorso scegliere per il cluster Talos:
Dato che il MID Server e gia deployato nel namespace sn del cluster con ServiceAccount RBAC configurato, il percorso raccomandato e la Modalita Credential-less (Fase C): URL = https://kubernetes.default.svc — nessuna credenziale da configurare — il MID Server si autentica autonomamente. Questo elimina la complessita di gestione dei token JWT su Talos (che non espone secrets legacy) e e il metodo nativamente supportato per MID Server deployati in-cluster.
